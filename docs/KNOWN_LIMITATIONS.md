# BusSense AI — Known Limitations & System Boundaries

This document provides a transparent, honest inventory of the technical boundaries, hardware constraints, and simulated features in the current BusSense AI implementation.

---

## 1. Hardware & Sensor Boundaries

1. **No Physical In-Vehicle CCTV Cameras:**
   - *Current State:* The computer vision engine (`backend/app/services/cv_occupancy.py`) operates in simulation mode (`CV_MODE=SIMULATION`), generating passenger boarding/alighting deltas based on stop arrival events.
   - *Resolution Path:* Ingest real RTSP streams from on-bus IP cameras using OpenCV VideoCapture when physical hardware is mounted.

2. **Simulated GPS Coordinates:**
   - *Current State:* Bus movement along Kerala corridors (Aluva ⇄ Kaloor ⇄ Infopark ⇄ Vyttila Hub) is generated by a 2.0-second background physics interpolator.
   - *Resolution Path:* Connect AVL GPS hardware dongles publishing NMEA 0183 or MQTT packets to `/api/buses/{id}/location`.

---

## 2. External Integration Boundaries

1. **No Live Government Transport Ministry (KSRTC) Integration:**
   - *Current State:* Vehicle schedules, stop sequences, and route configurations are stored directly in Supabase rather than querying a live KSRTC internal intranet API.
   - *Resolution Path:* Implement a GTFS-RT (General Transit Feed Specification Realtime) connector when Kerala Open Transit Data APIs become accessible.

2. **Sandbox Payment Gateway:**
   - *Current State:* Ticket bookings settle via a simulated instant payment engine (`PAYMENT_GATEWAY_MODE=SIMULATED`).
   - *Resolution Path:* Activate live Razorpay API keys and listen for cryptographically signed payment capture webhooks.

3. **Offline Conductor Sync:**
   - *Current State:* Conductor ticket validation makes direct HTTP requests to the backend server. If cellular data is completely severed inside a basement depot, validation requires connectivity restoration.
   - *Resolution Path:* Implement local SQLite offline caching on the conductor mobile terminal with asynchronous ledger reconciliation.

---

## 3. Data & Machine Learning Boundaries

1. **Synthetic Training Data for Demand Forecasting:**
   - *Current State:* The Ridge regression model is trained on synthetic Kerala corridor morning/evening rush-hour patterns.
   - *Resolution Path:* Retrain the model on longitudinal automated passenger counting (APC) logs gathered over 6+ months of real transit operations.

2. **Static RAG Knowledge Base:**
   - *Current State:* The transit assistant knowledge base contains core Kerala stage carriage fare rules, safety policies, and student concession regulations. It does not yet ingest dynamic daily detour circulars.
   - *Resolution Path:* Automate daily scraping of Kerala State Transport Authority gazettes and traffic police advisories.

---

## 4. Persistence & Transactional Boundaries (Updated in Phase H2)

1. **Transactional Persistence (Resolved):**
   - *Previous Limitation:* Tickets, QR validations, payments, incidents, and alerts were kept in volatile Python dictionaries (`ticket_service.tickets`, `INCIDENTS_STORE`, `ALERTS_STORE`), resetting on every backend restart.
   - *Status in Phase H2 (RESOLVED):* Authoritative persistence is established directly on Supabase PostgreSQL (`tickets`, `payments`, `ticket_validations`, `incidents`, `alerts`, `crowd_predictions`, `reports`). Data survives cold backend restarts and server failures.
2. **Offline Conductor Ledger Reconciliation (Remaining):**
   - *Current State:* QR validation is atomic against the Supabase database via `validate_ticket_atomic`. If conductor terminals lose connectivity entirely, scans require reconnecting.
   - *Resolution Path:* Future phase implementation of local encrypted SQLite ledger with cryptographically signed offline audit sync.

---

## 5. API Contract & Endpoint Boundaries (Updated in Phase H3)

1. **Backend Endpoint Surface (Resolved):**
   - *Previous Limitation:* Endpoints `/api/trips`, `/api/locations`, `/api/crowd`, `/api/predictions`, `/api/payments`, `/api/alerts`, and `/api/occupancy/predictions` were missing from the backend routing table, causing 404 errors.
   - *Status in Phase H3 (RESOLVED):* All 7 missing endpoint paths have been implemented, mounted, tested, and documented. 41 registered endpoints now form the standardized backend API contract.
2. **Native Mobile App Integration (Updated in Phase H4):**
   - *Previous Limitation:* Flutter native clients had not been initiated.
   - *Status in Phase H4 (RESOLVED):* The unified Flutter mobile codebase is established in `apps/mobile/` with shared API client, secure storage, and role routing.

---

## 6. Mobile Application Foundation Boundaries (Updated in Phase H4)

1. **Unified Flutter Mobile Foundation (Resolved):**
   - *Previous Limitation:* Zero Dart/Flutter mobile code was present in the repository.
   - *Status in Phase H4 (RESOLVED):* ONE unified Flutter codebase exists at `apps/mobile/` supporting both `PASSENGER` and `DRIVER_CONDUCTOR` roles through dynamic routing (`AppRouter`, `PassengerShell`, `ConductorShell`). The `AUTHORITY` role is cleanly redirected to the Next.js web operations console. State management is established via Riverpod (`AuthController`).
2. **Feature Screens Not Implemented (Boundary for Phases H5 and H6):**
   - *Current State:* Placeholder navigation destinations exist solely to verify routing correctness. The application intentionally contains NO production feature screens (no Live Map, no booking UI, no QR ticket UI, no active trip cockpit, no camera barcode scanner).
   - *Resolution Path:* Phase H5 implements the Unified Passenger Experience; Phase H6 implements the Conductor Cockpit.
3. **No Offline Ticketing or Offline Synchronization:**
   - *Current State:* The mobile foundation communicates exclusively over HTTP/REST via `ApiClient` to FastAPI. No offline caching or local database synchronization is implemented or claimed.
4. **Authority Separation:**
   - *Current State:* The Transport Authority experience remains 100% web-based (`frontend/` Next.js). There is NO Authority mobile app and NO mobile Authority screens.
